# TPPE v1 方案：多人填词造句网页游戏

> 状态：**待审阅**（2026-10-20）。审阅通过后按第八节顺序实施，每步一个 commit。
> 范围：v1 只做"本地能跑通、多人能玩"。部署到阿里云服务器（拉取、端口、自动更新）属于第二阶段，等你给服务器信息后另写部署计划。

---

## 一、需求复述（确认理解）

1. **房间**：任意玩家创建房间，拿到房间号；其他人输入房间号加入，同一房间的人看到同一条短句。
2. **短句模板**：预先准备一批短句，每条都含「时间、地点、人物、事件」四个空位，例如
   `{时间}，{人物}在{地点}{事件}。`。玩家看到的是挖空版本。
3. **分配**：每轮把四个空位随机分给房间里的玩家，每人填自己分到的那个元素，看不到别人填的内容。
4. **揭晓**：四个空都填完后，服务端拼成完整句子推给所有人；每个人的浏览器用**自带 TTS**（Web Speech API）朗读。
5. **循环**：揭晓后进入下一轮，重新随机抽模板、重新随机分配。
6. **词库**：四个元素各有一个词库，每个词限 **20 个字符以内**。玩家填过的词都存进去（去重）。
   填写时从该元素词库随机抽**至多 3 个**候选词供点选（库里不足 3 个就有几个给几个，空库时只有输入框），同时**永远保留**一个输入框可以自己打字；自己打的词也入库，下回就有可能被抽到。词库会随游玩越来越丰富。
7. **预置词**（2026-10-20 更正需求后新增）：冷启动时每个元素先预置 **15 个左右**词，让第一局就有候选可点；预置词和玩家词同等参与随机抽取。

## 三、技术选型（先比较再推荐）

**后端框架**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. **FastAPI + uvicorn + WebSocket** | 原生支持 WebSocket，房间状态实时推送；代码量小；一条命令启动 | 要装 2–3 个第三方包 |
| B. Flask + 前端轮询 | 最常见、上手简单 | 需要轮询，有延迟，接口也更啰嗦；实时性要再加 flask-sock 之类的包 |
| C. 纯标准库 `http.server` + 轮询 | 零依赖 | 并发和长连接都要手写，代码反而更多、更脆 |

**推荐 A**：多人房间的核心是"一个人操作，所有人马上看到"，WebSocket 最直接。依赖只有 `fastapi`、`uvicorn[standard]`，部署就是 `python -m tppe`。

**数据库**：**SQLite**（Python 标准库自带 `sqlite3`）。单文件 `data/tppe.db`，零运维；词库量级（万条）完全够用。以后要换 MySQL，只改 `db.py` 一个文件。

**房间状态**：放**进程内存**。重启服务后房间会丢，但词库在 SQLite 里不丢。v1 单进程部署，这样最简单。

**前端**：单个 `index.html` + 原生 JS + 内联 CSS，不用任何框架和构建工具。

**TTS**：浏览器 `speechSynthesis`，优先挑选中文音色（`lang` 以 `zh` 开头，优先带 Natural 的音色）。已知限制及对策：
- Chrome 要求用户先有点击才能出声 → 玩家进房间时必须点「加入」按钮，这次点击就算解锁了。
- 系统可能没有中文音色（多见于 Linux）→ 照样显示完整句子文字，并提示"当前浏览器无中文语音"。
- 长句可能被截断 → 模板都控制在 40 字以内；另提供「🔊 再读一遍」按钮。

## 四、短句模板

- 我预先写约 **80 条**模板，放在 `tppe/templates.json`，不进数据库（模板是内容资产，跟代码一起版本管理更直观）。
- 每条都恰好含 `{时间}{地点}{人物}{事件}` 四个占位，**语序和句式多样化**（陈述、传闻、新闻播报、日记体等），让不同的词填进去都尽量通顺、好笑。
- 「事件」统一按动宾短语设计（如"偷吃了月饼"），输入框里给出示例提示，引导玩家填出能接进句子的内容。
- 启动时校验每条模板四个占位齐全、各出现一次，不合格的直接报错，避免运行时才发现。

## 五、模块划分与接口（先定框架）

```
TPPE/
├── tppe/
│   ├── __main__.py      # 入口：python -m tppe [--host 0.0.0.0] [--port 8000]
│   ├── config.py        # 常量：字数上限、候选数=3、DB 路径、端口（可被环境变量覆盖）
│   ├── logging_setup.py # 日志：按模块分命名空间，输出到控制台 + logs/tppe.log
│   ├── db.py            # SQLite 访问层（词库 + 历史句子）
│   ├── wordbank.py      # 词库业务：校验、入库、随机候选
│   ├── templates.py     # 模板加载、校验、随机抽取、拼句
│   ├── room.py          # 房间与回合状态机（纯逻辑，不碰网络，方便测试）
│   ├── server.py        # FastAPI：HTTP 路由 + WebSocket 收发
│   ├── templates.json   # 短句模板
│   └── static/index.html
├── tests/               # pytest
├── data/                # SQLite 文件（gitignore）
├── docs/  计划/ 日志/开发日志.md
└── requirements.txt
```

**各模块输入 / 输出**

| 模块 | 主要函数 | 输入 → 输出 |
|---|---|---|
| `db` | `init_db()` | 无 → 建表（幂等） |
| | `insert_word(element, text)` | 元素名, 词 → 是否新词（已存在则只把使用次数 +1） |
| | `random_words(element, k, exclude=())` | 元素名, 个数 → 词列表（不足 k 个就返回实际个数，空库返回 []） |
| | `insert_sentence(template_id, filled, room_code)` | → 记录 id |
| `wordbank` | `normalize(text)` | 原始输入 → 去首尾空白、合并连续空白后的字符串 |
| | `validate(text)` | → `(ok, 错误原因)`，规则：长度在上下限内、不能是纯空白 |
| | `submit(element, text)` / `suggest(element)` | 包装 db，统一做校验 |
| `templates` | `load()` / `pick(exclude_recent)` / `fill(tpl, answers)` | 文件 → 模板列表；→ 随机模板（避开最近 10 条）；模板 + 四个答案 → 完整句子 |
| `room` | `Room.join / leave / start_round / submit / next_round` | 玩家事件 → 新状态 + 需要推送给谁的消息 |
| `server` | `POST /api/rooms` | → `{code}` 创建房间（4 位数字房间号） |
| | `WS /ws/{code}?name=` | 双向 JSON 消息（见下） |

**WebSocket 消息协议**

| 方向 | type | 内容 |
|---|---|---|
| 服务端→客户端 | `room_state` | 玩家列表、阶段（waiting / filling / reveal）、挖空的句子、每个空位"已填/未填"（**不含别人填的内容**） |
| 服务端→客户端 | `your_task` | 你要填的元素 + 3 个候选词 + 示例提示（同一人分到多个元素时依次下发） |
| 服务端→客户端 | `reveal` | 完整句子 + 各空位由谁填写 → 前端朗读 |
| 服务端→客户端 | `error` | 校验失败原因（如超长） |
| 客户端→服务端 | `start` / `submit {element, text}` / `next` | 开始游戏 / 提交 / 下一轮 |

**回合状态机**：`waiting`（等人，任何人点开始）→ `filling`（分配元素，收齐四个）→ `reveal`（拼句、入库、推送、朗读）→ 有人点下一轮 → `filling` …
- 玩家在 `filling` 阶段掉线：他没填的空位重新分给在线的人；房间空了就销毁。
- 词在**提交时**立即入库（不等整句完成），这样中途有人掉线，填过的词也不会丢。

## 六、数据库表

```sql
CREATE TABLE words (
  id INTEGER PRIMARY KEY,
  element TEXT NOT NULL CHECK (element IN ('time','place','person','event')),
  text TEXT NOT NULL,
  source TEXT NOT NULL DEFAULT 'player' CHECK (source IN ('seed','player')),
  use_count INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  UNIQUE (element, text)
);
CREATE TABLE sentences (
  id INTEGER PRIMARY KEY,
  room_code TEXT, template_id INTEGER, sentence TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);
```

随机候选用 `ORDER BY RANDOM() LIMIT 3`，万级数据量没有性能问题。

**预置词**：放在 `tppe/seed_words.json`（四个元素各约 15 个，都不超过 20 字符），`init_db()` 启动时用 `INSERT OR IGNORE` 写入，`source='seed'`。重复启动不会重复写入；玩家填了相同的词就按已有词处理。`source` 字段只用来区分来源，抽候选时一视同仁。

## 七、页面设计

一个页面、三个视图，手机和电脑都能用（窄屏单列布局）：
1. **大厅**：输入昵称 →「创建房间」或「输入房间号加入」。
2. **房间**：顶部是房间号（可一键复制）和玩家列表；中间大字显示挖空句子，四个空位用彩色标签表示（时间=蓝、地点=绿、人物=橙、事件=紫，已填的显示 ✅ 但不显示内容）；下方是我的任务卡：3 个候选词按钮 + 输入框 + 提交按钮 + 字数计数。
3. **揭晓**：完整句子逐段高亮，各段下方标出填写人，同时朗读；按钮「🔊 再读一遍」「下一轮」。

**安全**：玩家输入一律当纯文本渲染（`textContent`，不用 `innerHTML`），防止有人填 HTML 或脚本搞破坏；除此之外词的内容不做过滤，符合"存储没有任何限制"的要求。

## 八、实施步骤（每步一个 commit，开发在 `feat/game-v1` 分支）

1. 项目骨架：目录、`requirements.txt`、`config.py`、`logging_setup.py`、`__main__.py`
2. `db.py` + `wordbank.py` + `seed_words.json` 预置词 + 单元测试
3. `templates.json`（约 80 条）+ `templates.py` + 测试
4. `room.py` 状态机 + 测试（分配、人数不足和超员、掉线重分、多轮）
5. `server.py`（HTTP + WebSocket）+ 用 FastAPI TestClient 模拟多个玩家走完整回合的测试
6. `static/index.html` 页面 + TTS
7. 本地联调：开多个浏览器标签模拟 4 人玩若干轮，确认词库增长、候选词出现、朗读正常
8. 文档：README 运行说明、开发日志；合并到 main

**测试要锁住的规则**：候选至多 3 个（库不足时返回实际数量，空库返回 0 个）且不重复；超过 20 字符的词被拒；预置词重复启动不重复写入；永远可以手动输入；手动输入的词会入库；同一个词不重复入库；超长输入被拒；同一轮四个空位各恰好分配一次；别人的答案在揭晓前不会下发给其他玩家。

**日志命名空间**：`tppe.server`、`tppe.room`、`tppe.db`、`tppe.wordbank`。

## 九、第二阶段（部署，暂不做）

按《服务器自动拉取部署与自愈》手册：服务器 `git clone` → venv → `python -m tppe --host 0.0.0.0 --port <端口>`，用 systemd 托管（`Restart=always`），阿里云安全组放行端口，再配定时自动拉取和健康检查（加一个 `/health` 接口，v1 里会先留好）。需要你提供服务器系统版本、打算开放的端口，以及是否有域名。
