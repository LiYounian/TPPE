# 开发日志（时间倒序）

## 2026-10-20 · v1 实现：词库 + 模板 + 房间状态机 + WebSocket + 页面 + TTS

**做了什么**：按 v1 方案（Q2–Q5 用默认方案）在 `feat/game-v1` 分支实现全部功能，一步一个 commit：
- `db.py` / `wordbank.py`：words / sentences 两张表；词 1–20 字符（规范化后计数），候选至多 3 个且不重复，玩家输入一律入库并去重（已有的词 use_count+1）；`seed_words.json` 每个元素预置 15 个词，`INSERT OR IGNORE` 保证重复启动不重复写入。
- `templates.json`：80 条模板，启动时校验四个占位各出现一次；同一房间避开最近 10 条。
- `room.py`：waiting → filling → reveal 状态机；≥4 人时选 4 人填、上轮旁观的优先；<4 人时有人多填、依次下发；掉线后没填的空改派给待填最少的人，已填的保留；词在提交时立即入库；揭晓时写入历史句子。
- `server.py`：`POST /api/rooms` 建房（4 位房间号）、`GET /api/rooms/{code}`、`GET /health`、`WS /ws/{code}`；每个事件处理完后给全房间推 room_state + 各自的 your_task。
- `static/index.html`：大厅 / 房间 / 填写 / 揭晓，元素用颜色区分；揭晓时用 `speechSynthesis` 朗读（优先挑中文音色），「再读一遍」；玩家输入一律用 `textContent` 渲染。

**关键决策 / 教训**：
- `your_task` 带上 `round` 字段：广播是"状态 + 任务"成对推的，客户端/测试要靠轮次区分本轮任务和上一轮残留，不然会拿到旧任务。
- 用 Starlette TestClient 测多连接 WebSocket 时，必须 `with TestClient(app)` 共享一个事件循环，否则每条连接各开一个循环，跨连接广播会卡死。这是测试工具的问题，生产 uvicorn 只有一个事件循环，不受影响。
- 前端渲染任务卡时按 `轮次:元素` 去重，别人提交触发的广播不会清掉自己正在输入的内容。
- 在加入房间的那次点击里先播一段空语音，借用户手势解锁浏览器朗读（Chrome 的自动播放策略）。

**验证**：
- pytest 54 项全过（词库 20、模板 9、房间 20、服务端 5），锁住：候选 ≤3、空库只能手填、超过 20 字符被拒、预置词幂等、四个空各分配一次、旁观者轮换、掉线改派、揭晓前答案不外泄、多轮模板不重复。
- 本地联调（Chrome 内置浏览器 1 人 + 脚本模拟 3 人）：建房 → 4 人加入 → 两轮完整填写 → 揭晓并朗读（macOS「婷婷」音色，已确认 `speak` 收到完整句子）→ 其余 3 人掉线 → 单人局 4 个空依次下发；手打的词按 `source=player` 入库，点选预置词后 use_count+1，两条完整句子入库；手机宽度布局正常，控制台无报错。
- 没测：Windows / Edge 下的音色选择，真实多设备、跨网络游玩（等部署后再测）。

**遗留 / 下一步**：部署到阿里云（systemd + 安全组放行端口 + 定时自动拉取，参照内部的《服务器自动拉取部署与自愈》手册），需要服务器系统版本、端口、是否有域名。

**分支 / PR**：`feat/game-v1`（基于 `docs/plan`，包含方案文档），合入 main。
